# GitHub Workbench architecture

GitHub Workbench is a GitHub CLI extension named `gh-workbench`. The executable
starts a loopback Go service and serves an embedded React application. One
process represents the active `gh` account and aggregates relevant open issues
and pull requests through account-wide GitHub search. Relevance means authored,
assigned, mentioned, reviewed, or review-requested. Account caches are isolated
by GitHub host and viewer login.

## Runtime and data flow

1. `gh workbench` resolves the active keyring-backed GitHub CLI account.
2. Account-wide GraphQL searches discover open items authored by, assigned to,
   mentioning, or reviewed by the viewer.
3. A review-requested search marks pull requests currently awaiting the viewer.
4. Results are deduplicated across repositories and reconciled as one account
   resource. A missing item leaves snapshots immediately and remains cached for
   three searches before deletion.
5. Relevant work items receive adaptive latest-activity polls. Due items are
   coalesced into GraphQL batches of up to 50, while pull-request inline review
   comments use conditional REST requests.
6. Each relevant pull request receives an independent REST reaction poll.
7. SQLite stores GitHub data, ETags, the cached inline-review candidate, and the
   next polling time.
8. A bounded worker pool leases due resources and publishes aggregate snapshots
   to browsers over WebSocket.

The scheduler treats every resource as a small state machine. A change heats the
resource to a ten-second interval; successive unchanged results double the
interval until its activity-based cap. GitHub rate-limit responses pause the
account queue until the reset time. Activity batches share one worker job while
retaining each resource's revision, ETag, outcome, and backoff. An account-wide
gate starts at most one GitHub request per second while workers overlap network
latency. Material data and error changes publish a full snapshot; stable polls
remain within the scheduler until the queue becomes idle.

## Boundaries

- `cmd/gh-workbench` parses flags and handles process signals.
- `internal/app` resolves the active account, wires concrete dependencies, and
  owns startup and shutdown.
- `internal/github` is the only package that calls GitHub. GraphQL owns
  cross-repository discovery and batched activity refreshes; REST owns inline
  review-comment and pull-request reaction refreshes.
- `internal/store` is the only package that reads or writes SQLite.
- `internal/syncer` owns the global search resource, batched activity resources,
  pull-request reaction resources, polling cadence, and bounded concurrency.
- `internal/server` owns the local HTTP/WebSocket protocol and session checks.
- `internal/model` contains types shared across backend boundaries.
- `internal/webui` embeds assets generated by `pnpm --dir web build`.
- `script/build-release.sh` cross-compiles tagged extension assets and verifies
  their embedded version.
- `web/src` owns browser UI state and rendering.

## Local security

The server listens on a random `127.0.0.1` port. Each process generates a
cryptographically random session token. The launch URL exchanges that token for
a process-specific `HttpOnly`, `SameSite=Strict` cookie. API and WebSocket
handlers validate the cookie, host, and origin.

## Engineering rules

Keep the dependency direction toward `internal/model`. Pass narrow interfaces
at package boundaries. Prefer direct constructors and standard-library
facilities over framework abstractions.

Generated files under `internal/webui/dist` stay outside Git. Supported build
and test entry points generate the frontend before compiling packages that
embed it.

## Checks

Run `make check` after code changes. Run `make build` to verify the embedded
frontend and final Go binary together. Run `make test` for the shorter unit-test
path.
